# Jim brief — registry-driven client: new cities appear without an app release

**Lane:** bug-fix / product mode (CLAUDE.md "Bug-fix lane"). **Date:** 27 Sep 2026. **Authority:** Tim, in chat 27 Sep 2026: "Go ahead and brief Jim to make the client registry-driven." This authorises shared product UI, a new/extended `api/*.js` endpoint, `scripts/`, `qa/`, and one-paragraph edits to docs/live-flip-checklist.md and .claude/agents/mark.md. **tim-review:** no (explicitly requested), but the PR description must have a "What changes for riders" section for Tim to read. The `/api/next-train` response shape does not change.

## Problem
Every city flip today needs a new Android and iOS release because the installed client bundles "which cities exist" in seven hand-maintained copies, kept in sync only by qa/live-city-lists-sync.mjs:
- public/city-session.js: `MULTI_CITY_IDS`, `COUNTRIES` (picker tree), `CITY_BOUNDS`
- public/app.js: `LIVE_CITY_IDS`, `NEARBY_MULTI_CITY_IDS`
- public/journey-model.js: `PERSISTED_CITY_IDS`, `PERSISTED_COUNTRY_IDS`
- public/brisbane-dogfood.js: `MULTI_CITY_IDS`
- public/city-directions/<city>.json bundled per city (45 files, ~700 KB), fetched by brisbane-dogfood.js
The server already knows the answer: lib/providers/registry.js is the source of truth, `api/cities.js` lists it (nobody calls it), `api/city-stations.js` / `api/country-stations.js` serve catalogs, and the "Write city-directions JSON" CI workflow regenerates public/city-directions on every master push, so the deployed site always has the JSON for every city.

## Design (what to build)
1. **City manifest endpoint.** Extend `api/cities.js` (keep `contractVersion`, bump to 2, keep backwards-compatible fields) so that for every `status: "live"` city it returns: `id`, `displayName`, `country: { id, name }`, `timeZone`, `bounds` (the CITY_BOUNDS box or boxes), `modes`, `nearbyEligible` (today's NEARBY_MULTI_CITY_IDS membership — derive it from a registry field you add, not a client list), and `directionsVersion` (a short content hash of that city's directions JSON). Include a top-level `countries` array in picker order with `regions` per country (this replaces `COUNTRIES`). Move `CITY_BOUNDS` and the picker order/country names to server-side data (lib/cities/country-regions.js is the natural home) so the client holds none of it. Cache-Control stays `s-maxage=300`. Planned/retired cities are NOT in the manifest — no "Coming Soon" (docs/jim-brief-no-coming-soon-picker.md).
2. **Client loads the manifest.** On boot, fetch `/api/cities`; on success persist `{fetchedAt, manifest}` to localStorage (`nextTrainCityManifest`). Resolution order: fresh network → cached copy (any age; show nothing about staleness unless > 7 days, then a quiet console warning) → **bundled seed**. The seed is `public/city-manifest.seed.json`, generated at build by a new `scripts/write-city-manifest.mjs` from the registry, wired into `cap:sync` and the "Write city-directions JSON" workflow, so a fresh install with no network still shows today's cities. Replace all seven lists with accessors over the loaded manifest (`isLiveCity(id)`, `liveCityIds()`, `countries()`, `boundsFor(id)`, `isNearbyEligible(id)`). Persistence (journey-model.js) must accept ANY city id present in the loaded manifest or in the saved data itself — never drop a saved journey because a city is missing from a hardcoded set; if a city later goes `retired`, the journey still loads and shows the existing "not available" path.
3. **Directions JSON on demand.** brisbane-dogfood.js fetches `/city-directions/<city>.json?v=<directionsVersion>` from the deployed site (same-origin in the web app; the API origin in Capacitor — reuse however `/api/*` is addressed there), caches the body in localStorage keyed by city+version, falls back to cache when offline. Stop bundling public/city-directions/*.json into the app (scripts/prune-ship-assets.mjs) EXCEPT as a seed for the cities in the seed manifest, so first launch offline still works for existing cities.
4. **Flip becomes one line again.** After this lands, a flip PR changes `status` in registry.js (+ the registry's picker/country/bounds data for a first-city-in-country), regenerates the seed via the script, and nothing else in public/. Rewrite qa/live-city-lists-sync.mjs to assert: (a) `/api/cities` live set === registry live set, (b) `grep` finds no hardcoded city-id lists left in public/*.js (allowlist the seed file), (c) the seed file equals the script's output. Update docs/live-flip-checklist.md and the "flip commit" paragraph in .claude/agents/mark.md to the new one-line shape (one paragraph each, cite this brief).
5. **Browser QA.** New `qa/registry-driven-client.mjs`: (a) stub `/api/cities` (fixture mode, see TESTING.md) with an extra fake live city "testville" and assert it appears in the picker and `isLiveCity("testville")` is true with no code change; (b) block the network after a first load and reload — picker still shows the cached cities; (c) clear storage and block network — seed cities appear; (d) a saved journey for a city absent from a stubbed manifest still loads. Register it in qa/run-all.mjs smoke tier.
