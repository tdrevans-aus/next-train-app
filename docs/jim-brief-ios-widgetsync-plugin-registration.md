# Jim brief: iOS WidgetSync plugin is never registered — Release builds show test ads, widget never syncs

Written 26 Sep 2026 by the Mac session (Bob) while verifying a Release simulator build of master
(64ba0d74) for the first App Store submission (3.0.4).
tim-review: no (native wiring; no copy/IA/API change)

## Symptom

A **Release** build of the iOS app shows Google's *test* banner ("Test mode — This is a 728x90 test
ad"), i.e. production iOS would earn nothing from ads. Production `site-config.json` has
`admobTestMode: false` and a real `admobBannerId`.

## Cause (confirmed by reading code + native call log)

- `web-sources/ads-native.mjs` `isNativeReleaseBuild()` asks the custom native plugin
  `WidgetSync.isDebugBuild()`; on any failure it caches `cachedReleaseBuild = false`, and
  `resolveEffectiveTestMode()` then returns **true** (test ads) for every native build.
- `ios/App/App/WidgetSyncPlugin.swift` implements `isDebugBuild` correctly (`#if DEBUG`; the
  Release config has no DEBUG condition), **but the plugin is never registered with the bridge**:
  - Capacitor 8 auto-registers only classes in `ios/App/App/capacitor.config.json`
    `packageClassList`, which `cap sync` generates from npm plugins:
    `['AdMobPlugin', 'GeolocationPlugin', 'NativePurchasesPlugin', 'SentryCapacitorPlugin']` — no
    `WidgetSyncPlugin`.
  - `Main.storyboard` uses the stock `CAPBridgeViewController`; there is no subclass calling
    `bridge?.registerPluginInstance(WidgetSyncPlugin())`.
  - Native call log from the Release build shows `To Native -> AdMob …` calls but never
    `To Native -> WidgetSync …`: the JS proxy rejects as unimplemented before reaching native.
- Same root cause means **every** WidgetSync call fails on iOS: `syncSettings` (the home-screen
  widget never receives the user's journeys/settings from the app), `getLaunchDeepLink` /
  `peekLaunchDeepLink` / `clearLaunchDeepLink` (widget-tap deep links), `getWidgetInstanceCount`,
  `isAvailable`. Android is unaffected (its plugin is registered in `MainActivity`).

## Fix (suggested)

Standard Capacitor local-plugin registration: add `ios/App/App/MainViewController.swift`,
a `CAPBridgeViewController` subclass overriding `capacitorDidLoad()` to call
`bridge?.registerPluginInstance(WidgetSyncPlugin())`; point `Main.storyboard`'s view controller
`customClass` at it (customModule `App`); add the file to the App target in `project.pbxproj`.
Don't hand-edit `capacitor.config.json` (regenerated by `cap sync`).

## Also in scope: pin sentry-cocoa so Archive can't drift

Found by the release-readiness run (PR #456): in a fresh checkout, `npm ci && npx cap sync ios`
then `xcodebuild` let SPM resolve `sentry-cocoa` to 9.29.2, ahead of the committed
`Package.resolved` (9.26.0), and the build failed with "cannot find 'PrivateSentrySDKOnly' in
scope" in `SentryCapacitorPlugin.swift`. It only built with `-onlyUsePackageVersionsFromResolvedFile`.
Tim's Xcode Archive shouldn't depend on remembering a flag. Find where the `sentry-cocoa`
requirement comes from (the `@sentry/capacitor` package's SPM manifest, via
`ios/App/CapApp-SPM/Package.swift`, which `cap sync` regenerates) and make the resolution
deterministic at the known-good version — e.g. a `patches/` entry for `@sentry/capacitor` pinning
`exact: "9.26.0"` (patch-package already runs on install), or whatever survives `cap sync`.
Explain the choice in the PR. Verify: fresh worktree, delete any `Package.resolved` changes and
SPM caches for the derived-data path, `npm ci && npx cap sync ios`, plain Release `xcodebuild`
**without** `-onlyUsePackageVersionsFromResolvedFile` → builds, and `Package.resolved` still says 9.26.0.
